--------------------------------------------------------------------------------
P. RESEARCH PURPOSE — WHY COMPETITION-GRADE BASELINES ARE BEING ADDED
--------------------------------------------------------------------------------

Where the project stands
  Stages 1-5 established the data pipeline, the 12 M6 rolling-origin contexts,
  raw inference for three time-series foundation models (TSFMs) and a single,
  shared M6 quintile/RPS evaluator. The headline results were:

    Naive equal-probability benchmark        0.160000
    Chronos-2 120M + spatiotemporal copula   0.165418
    Chronos-2 120M + independent sampling    0.165559
    Financial Chronos Small 46M              0.179368
    Chronos T5 Base 200M                     0.226899

  Every TSFM tested is beaten by a forecast that assigns 0.2 to each quintile.
  That is an informative result, but on its own it cannot distinguish between
  two very different explanations: (a) the M6 ranking task is close to
  unpredictable at this horizon, so nothing much beats the uniform forecast, or
  (b) the TSFMs specifically are poorly suited to it, while conventional
  feature-based learners do better.

Why baselines resolve this
  A competition-grade supervised baseline that was actually built for the M6
  ranking task provides the missing reference point. If well-tuned LightGBM and
  Random Forest models also fail to beat 0.16, that is evidence for (a) - a
  statement about the task. If they beat it, that is evidence for (b) - a
  statement about the TSFMs, and a much stronger contribution: it would show
  that zero-shot foundation models underperform purpose-built feature-based
  models on cross-sectional financial ranking.

Methodological reference: Samartzis
  The primary reference is Panagiotis Samartzis, "Predicting the Relative
  Performance among Financial Assets: A Comparative Analysis of Different
  Approaches" (International Journal of Forecasting), with the accompanying
  implementation placed in this repository under `Relevant Context/`:
    Generate_forecasts.py    data preparation, feature construction, the
                             tuning/forecast loop and the model registry
    all_models.py            the model wrappers (LGBM, RF and many others)
    Calculate_metrics.py     evaluation metrics
    RPS and IR calculation.py  the official M6 scorer
    Data_M6.xlsx             the data template (sheets: Tickers, Close, Open,
                             High, Low, Volume) - a structure template, not
                             populated data
    Universe_M6.xlsx         the 100-asset M6 universe
  Samartzis is directly relevant because he addresses exactly this task (M6
  quintile probabilities over the same 100 assets) with feature-based learners,
  and his LGBM and RF configurations are competition-grade rather than toy
  baselines.

This is an adaptation, not a reproduction
  We are re-implementing SELECTED Samartzis baselines (initially LightGBM and
  Random Forest) INSIDE this project's existing methodology and evaluation
  framework. Concretely that means:
    - the core modelling ideas and engineered predictors are preserved where
      they are appropriate to our design;
    - implementation details are adapted where necessary so the baselines
      remain directly comparable with the TSFM results already produced -
      above all, they must be scored by the SAME evaluator
      (scripts/evaluate_m6_rps.py), against the SAME ground truth built from
      Data/assets_m6.csv, over the SAME 12 official M6 rounds;
    - preprocessing decisions from the original repository are NOT copied
      simply because they are there. Several of them (forward/backward fill,
      KNN imputation, ECOD outlier replacement, winsorising) conflict with the
      deliberate "no fabricated observations" stance taken in Stages 1-3 of
      this project, and each will be evaluated on its merits and documented
      as adopted, modified or rejected.
  When the modelling stage is implemented, the documentation must state for
  each component whether it came from Samartzis unchanged, was modified, or was
  designed for this project - and why.

Scope of the current stage
  RAW DATA ACQUISITION ONLY. No preprocessing, feature engineering, labelling,
  training, tuning, forecasting or evaluation has been performed.

Q. DATASET D — COMPETITION BASELINE OHLCV DATA (RAW ACQUISITION)
   (executed 2026-08-08)
--------------------------------------------------------------------------------

Why a separate dataset was needed
  None of the existing datasets can serve the feature-based baselines:
    Dataset A (Yahoo + EODHD repairs, adjusted close only, 2020-01-01 onward)
      is too short for features that look back ~11 months before a 2010
      training row, and carries only one field.
    Dataset C (EODHD adjusted close, 2012-03-05 .. 2022-03-04) was collected
      for possible TSFM fine-tuning. It is adjusted-close only and starts too
      late, so it cannot support Open/High/Low/Volume features or a 2010 start.
    The processed panels, rolling-origin contexts, model outputs and evaluation
      outputs are all downstream artifacts of Dataset A and are not raw inputs.
  Dataset D is therefore a new RAW dataset, kept entirely separate from all of
  the above. Nothing in Dataset A, Dataset C, the processed data, the rolling
  contexts, the model outputs, the evaluation results or the exploratory
  Testing_What_Works/ outputs was modified by this stage.

Relationship to the other datasets
  Dataset D overlaps Dataset A in time (2020-2023) and Dataset C in time
  (2012-2022), but it is an independent download with a wider field set. The
  overlap with Dataset A is used ONLY as an identity check - to confirm that the
  security retrieved under each EODHD identifier is the intended M6 asset. No
  Dataset A or Dataset C value is ever copied into Dataset D, and no Dataset D
  gap is patched from them.

Universe
  Exactly the 100 official M6 assets already used throughout the project, taken
  from the project's own authoritative ordering (the column order of
  Data/processed/rolling_origins/round_01_context.csv) rather than reconstructed
  independently. Verified: the retrieved universe equals that list exactly.
  Cross-check against the reference material: Samartzis's Universe_M6.xlsx
  contains the same 100 assets with one naming difference - he lists EG where
  this project uses the canonical M6 ticker RE. That is independent
  corroboration of the RE -> EG mapping this project validated in Stage 1B.

Provider
  EODHD only, through the project's existing secure configuration: the token is
  read from the git-ignored local env file, and is never printed, written into
  code, saved into any output, included in documentation or committed. All
  provider error text is redacted before being raised (verified in practice
  during this stage - a network failure surfaced the URL with the token shown as
  ***REDACTED***). Before any bulk download the script confirms the env file is
  untracked by git and covered by .gitignore.

Requested date range
  2009-01-01 through 2023-02-03 inclusive. The end date is the final M6
  evaluation date, matching both this project's round schedule and Samartzis's
  own M6 sample (`end_oos_date = '2023-02-03'` in Generate_forecasts.py).

R. THE 2009 WARM-UP HISTORY — WHY THE RANGE STARTS BEFORE THE MODELLING SAMPLE
--------------------------------------------------------------------------------

The intended modelling sample begins in 2010, consistent with the Samartzis
feature-based implementation. The 2009 observations exist purely so that the
lagged and rolling predictors are DEFINED for the earliest 2010 training rows.
They are feature-construction history: they are not training observations, not
an additional evaluation period, and they change nothing about the M6
experiment, whose 12 rounds remain exactly as established in Stage 3
(origins 2022-03-04 .. 2023-01-06, evaluation ending 2023-02-03).

The binding constraint is `feat_6` in Generate_forecasts.py:

    feat_6 = monthly_returns.shift(20*11)

`monthly_returns` is itself a four-week (20 business day) return, and it is then
shifted back 20 x 11 = 220 business days. A row dated t therefore depends on
price information reaching back roughly 220 + 20 = 240 business days - about
eleven to twelve calendar months. Several other predictors add their own
lookback on top of a 20-day shift:

    feat_1 = returns_df.rolling(60).std().shift(20)      60 + 20  =  80 days
    feat_2 = returns_df.rolling(60).max().shift(20)      60 + 20  =  80 days
    feat_3 = log(volume * close / 1000).rolling(40).sum().shift(20)
                                                          40 + 20  =  60 days
    feat_4 = (|returns| / feat_3).rolling(60).sum().shift(20)
                                                          up to 120 days
    feat_5 = quarterly_returns.shift(20)                  60 + 20  =  80 days
    feat_6 = monthly_returns.shift(20*11)                220 + 20  = 240 days

So the deepest requirement is ~240 business days before the first modelling
observation. For a training row in early January 2010 that reaches back into
roughly January-February 2009. Requesting from 2009-01-01 provides that warm-up
with a small margin.

Consequences to respect in the next stage
  - Rows before roughly 2010 must be dropped from the TRAINING sample rather
    than kept with partially-defined features.
  - Assets that listed after 2009 will have `feat_6` undefined for their first
    ~240 business days. That is genuine missing information, not a data error,
    and the handling of it is a modelling decision to be documented then.
  - Nothing about the 2009 data licenses any change to the evaluation window.

--------------------------------------------------------------------------------
S. RETRIEVED FIELDS AND WHY EACH IS KEPT
--------------------------------------------------------------------------------

For every asset-date EODHD supplies, Dataset D stores the raw values of:

  date            trading date as reported by the provider
  open            used by Samartzis for two predictors: the intraday
                  open-to-close move, `open_close = (close - open) / open`, and
                  the overnight gap, `open_close_gap = (open - close[t-1]) /
                  close[t-1]`. Both capture short-horizon price pressure that a
                  close-only series cannot express.
  high, low       used for the intraday range proxy,
                  `high_low = (high - low) / close`, a simple realised-volatility
                  measure that does not require a long estimation window.
  close           the raw (unadjusted) closing price. This is what Samartzis's
                  template supplies and what his features consume, including the
                  dollar-volume term inside `feat_3`.
  adjusted_close  NOT used by Samartzis (his Data_M6.xlsx has no adjusted-close
                  sheet). It is retained here as a deliberate adaptation,
                  because the rest of this project - Dataset A, the Stage 2 log
                  returns, the rolling contexts and every TSFM result - is built
                  on adjusted close. Keeping both fields means the next stage can
                  decide, and document, whether the baselines' return
                  construction should follow Samartzis (raw close) or this
                  project's existing convention (adjusted close), without another
                  download. See the KR data-quality note in section T before
                  making that choice.
  volume          used directly in `feat_3` (a 40-day rolling sum of log dollar
                  volume, a liquidity/size proxy), in `feat_4` (an Amihud-style
                  illiquidity ratio of absolute return to dollar volume) and in
                  the raw volume change `vol_change = volume.pct_change(1)`.

Retained exactly as supplied. No returns of any kind were computed into the
stored dataset, no field was rescaled, and no derived column was added beyond
the two provenance columns (`symbol`, `eodhd_identifier`) that make the long
format self-describing.

T. ACQUISITION RESULT, IDENTIFIERS AND DATA-QUALITY FINDINGS
--------------------------------------------------------------------------------

Outcome
  100 of 100 assets retrieved successfully; no asset failed, none was dropped
  and none was substituted. 315,042 asset-date rows spanning 2009-01-02 (the
  first trading day on or after the requested 2009-01-01) to 2023-02-03. All six
  price/volume fields are present with no missing values in any retrieved row.

Subscription and API behaviour
  The subscription was verified before any bulk download (active monthly plan,
  100,000 requests/day, ~36 used at the time), and the historical EOD endpoint
  was probed AT the 2009 start date specifically to confirm that history reaches
  that far back rather than assuming it.
  A transient network outage did occur: for roughly ten minutes eodhd.com was
  unreachable from this machine (DNS resolved, TCP connections timed out) and
  three successive attempts failed before the first asset was downloaded. This
  was not a subscription problem - the same token had completed 100 downloads
  for Dataset C shortly before, and connectivity returned by itself. In response
  the shared client gained a proportional retry (4 attempts with a 15/30/45s
  backoff, network errors only; HTTP status errors are not retried). The
  acquisition then completed in one pass.

EODHD identifier mappings (11 of 100 do not map to <TICKER>.US)
  RE -> EG.US
      Everest Re Group was renamed Everest Group; EODHD serves the history under
      the post-rename code. The naive RE.US would be a DIFFERENT security. This
      mapping was validated in Stage 1B against the official M6 price file and
      is reused here, and is independently corroborated by Samartzis's universe
      file listing EG.
  DRE -> DRE.US, WRK -> WRK.US
      Also confirmed in Stage 1B; both resolve directly despite being delisted
      or merged after the competition.
  Ten London-listed ETFs map .L -> .LSE:
      HIGH.L, IEAA.L, IEFM.L, IEVL.L, IUMO.L, IUVL.L, JPEA.L, MVEU.L, SEGA.L,
      SPMV.L
  The remaining 89 tickers resolved as <TICKER>.US on the first attempt,
  including the hyphenated BF-B -> BF-B.US. (Note that Samartzis renames this
  asset to BF.B for his provider; our provider does not require that.)
  The resolver tries candidates in order and records every identifier attempted.
  If all candidates fail the asset is recorded as failed - it is never silently
  replaced with a similar-looking security.

Identity verification
  Each retrieved series was checked against Dataset A over their overlap by
  comparing daily returns (correlation and median absolute difference). 99 of
  100 assets matched cleanly. Dataset A was used only as a reference; it never
  contributed a value to Dataset D.

DATA-QUALITY FINDING — KR adjusted_close has a break on 2022-10-21
  KR (Kroger) was flagged by the identity check with an adjusted-close return
  correlation of 0.944 against Dataset A, below the 0.98 threshold. Investigation
  shows the identifier is CORRECT and the raw prices are sound - it is the
  provider's adjustment factor that is broken:

    date        close    adjusted_close   adj/close
    2022-10-17  42.11    32.2524          0.7659
    2022-10-20  42.17    32.2983          0.7659
    2022-10-21  43.63    39.8974          0.9144   <-- factor jumps 19.4%
    2022-10-24  43.99    40.2266          0.9144

  The adjustment ratio is constant either side of 2022-10-21 and steps
  discontinuously on that date, manufacturing a spurious +23.5% one-day return
  in adjusted_close where the true move was about +3.5%. Kroger's raw close
  series is clean: its returns correlate 0.9995 with Dataset A.
  A scan of all 100 assets found only two with any daily adjusted-close return
  disagreement above 1% versus Dataset A - KR (one day, 20.1%) and COP (two
  days, max 1.5%, consistent with ordinary dividend-timing differences between
  providers rather than a break).
  Why this matters for the next stage: 2022-10-21 falls inside M6 Round 9
  (forecast window 2022-10-17 .. 2022-11-11). If the baselines construct returns
  from Dataset D's adjusted_close, KR would carry a fabricated 23.5% move inside
  a scored round. Samartzis's own features use raw close, which is unaffected.
  This must be resolved explicitly before preprocessing - the options are to use
  raw close (following Samartzis, and unaffected), to use adjusted close with a
  documented correction for this single break, or to source the adjustment from
  another dataset. No correction has been applied here, because this stage is
  acquisition only and the raw provider output is preserved as received.
  Note that this does NOT affect any existing result: the M6 evaluation targets
  are built from Data/assets_m6.csv, and the TSFM inputs come from Dataset A.

Assets with shorter genuine histories (27 of 100)
  Retained exactly as supplied; no pre-inception period was backfilled,

    SEGA.L 2009-06-04, VRSK 2009-10-07, DG 2009-11-13, CHTR 2010-01-05,

--------------------------------------------------------------------------------
Z. DATASET D — USED EXACTLY AS ACQUIRED, INCLUDING THE KNOWN KR DEFECT
--------------------------------------------------------------------------------

Decision
  Dataset D is used exactly as it exists on disk. It was NOT re-downloaded, NOT
  repaired, NOT patched from another provider and NOT special-cased anywhere in
  preprocessing. `scripts/preprocess_dataset_d.py` hashes the raw file (SHA-256)
  before and after every run and aborts if a single byte changed; the run that
  produced the current artifacts confirmed it unchanged.

The KR limitation, accepted deliberately
  As established in section T, EODHD's adjusted-close series for KR (Kroger)
  contains an erroneous corporate-action adjustment on 2022-10-21: the
  adjustment ratio steps discontinuously by ~19.4% on that date, manufacturing a
  one-day adjusted-close move of about +23.5% where the genuine market move was
  about +3.5%. The provider appears to have associated an unrelated $6.85
  special dividend with KR. The identifier is correct and KR's RAW close series
  is clean.

  Because this project's return convention is adjusted close (section AC), that
  spurious move flows into KR's daily log return on 2022-10-21
  (log return 0.2113, i.e. +23.5%), and therefore into:
    - KR's `feat_ret_4w_recent`, `feat_vol_3m`, `feat_max_ret_3m` and
      `feat_abs_ret_to_volume_3m` at the origins whose trailing windows contain
      2022-10-21 (the origins from 2022-11-11 onwards for the 20-day windows,
      and from 2022-11-11 through 2023-01-06 for the 60-day windows);
    - KR's daily cross-sectional quintile on 2022-10-21, hence its
      `feat_rank5_freq_4w` at nearby origins, and marginally the daily quintile
      boundaries of the other 99 assets on that one day;
    - KR's Dataset-D-derived HISTORICAL four-week target for the origin
      2022-10-14 (target window 2022-10-17 .. 2022-11-11), which coincides with
      M6 Round 9.

  It does NOT affect the official M6 evaluation in any way. The evaluation
  ground truth is built by `scripts/evaluate_m6_rps.py` from
  `Data/assets_m6.csv` — the official competition price file — and never from
  Dataset D. See section AM.

  Why no correction was applied. An earlier option was to replace KR with Yahoo
  data, but mixing two providers' adjustment semantics inside one panel creates
  more problems than it solves (different dividend-timing conventions, different
  adjustment recomputation histories) and would have made KR the only asset in
  the panel whose returns come from a different provider. Retaining the defect
  and documenting it keeps the dataset internally consistent and the limitation
  explicit. It is a documented data-provider limitation of this experiment.

  Note that this is deliberately NOT treated as an "outlier" to be suppressed:
  see section AB. A confirmed provider defect and a genuine extreme market move
  are conceptually different things, but in this implementation neither is
  altered.

Dataset C
  Untouched. Dataset C is the adjusted-close-only EODHD panel collected for
  possible TSFM fine-tuning. It was neither read, regenerated, overwritten nor
  conflated with Dataset D at any point in this stage.

AA. STAGE 6A — SHARED WEEKDAY CALENDAR AND FILL POLICY
    (scripts/preprocess_dataset_d.py)
--------------------------------------------------------------------------------

This is the COMMON preparation shared by both preprocessing variants. It
reproduces the convention already established for Dataset A in Stage 2
(`scripts/preprocess_dataset_a.py`) rather than inventing a new interpretation;
only the span differs, because Dataset D needs 2009 warm-up history.

Calendar
  One shared Monday-to-Friday calendar, `pd.date_range(freq='B')`, spanning
  2009-01-02 .. 2023-02-03 = 3,676 dates. Weekends excluded; public holidays are
  RETAINED as calendar dates (they carry no new information but keep every asset
  on one index). Individual exchange calendars are deliberately not used: the
  universe mixes US and London listings, and all later work is cross-sectional.
  Reindexing added 71 weekday dates that were absent from the raw union
  calendar. All 13 M6 Friday anchors exist on this calendar (verified).

  2009-01-02 is the first genuine observation in Dataset D (2009-01-01 was a
  holiday), so the calendar starts there rather than at the requested 2009-01-01.

Fill policy
  Forward fill only, applied per asset per field, and only AFTER that asset's
  first genuine observation. `pandas.ffill` never fills before the first valid
  value, which is exactly the required rule, and this is additionally asserted
  per asset per field in `validate_outputs`.
    - Rationale for forward filling: it aligns assets to the common weekday
      calendar without inventing price movement. On a date with no new
      observation the carried-forward price implies a zero return, which is the
      faithful representation of a position that could not change value.
    - Rationale for prohibiting backward filling: it would manufacture price
      history for an asset before it existed.
    - No interpolation, no averaging, no smoothing, no cross-asset substitution.
  Total cells forward-filled across all six fields: 77,868.

Genuine later inception (27 of 100 assets)
  Preserved as missing. The full list is in section T and in
  `Data/metadata/dataset_d_preprocessing_summary.csv` (column
  `leading_missing_weekdays`), ranging from DG (225 leading missing weekdays) to
  OGN (3,225).

Post-delisting (DRE)
  DRE's final genuine observation is 2022-10-03 (Duke Realty acquisition). Its
  final price is carried forward over the 90 subsequent weekdays through
  2023-02-03, so every DRE log return after 2022-10-03 is exactly zero. This is
  the treatment established in Stage 2 and is asserted explicitly. It coincides
  with the official M6 rule that DRE's competition return is zero after
  acquisition. NOTE: DRE's last genuine observation also carries volume 0, so
  forward filling propagates a zero volume across those 90 weekdays; the
  consequence for the volume features is described in section AI.

Field semantics
  All six raw fields (open, high, low, close, adjusted_close, volume) are
  carried onto the calendar and forward-filled with the same rule. Every asset's
  inception date is verified to be identical across the six fields. Only close,
  adjusted_close and volume are consumed by the ten selected predictors; open,
  high and low are materialised anyway so that the processed representation of
  Dataset D is complete and no re-run is needed if the excluded intraday
  features (section AH) are ever revisited.

Raw data is never mutated to accomplish alignment. Stage 6A writes NEW processed
files; the raw long-format CSV is read-only.

AB. OUTLIERS — NO ECOD, NO WINSORISATION (DELIBERATE DEPARTURE)
--------------------------------------------------------------------------------

Samartzis preprocesses outliers as follows (`prepare_data` in
Generate_forecasts.py): for every asset he fits `ECOD(contamination=0.01)` to
that asset's return series, collects the flagged days, keeps those on which only
ONE asset was flagged ("idiosyncratic days"), and replaces the flagged return
with the asset's own 1st or 99th return percentile depending on sign — plus an
unconditional rule that any |return| > 0.5 is replaced the same way.

This component is NOT adopted. Nothing in this project applies ECOD,
winsorisation, percentile clipping/capping or any generic outlier replacement.

Rationale
  Large financial returns are frequently genuine information rather than errors,
  and this is a cross-sectional RANKING task in which the extreme movers are
  precisely the observations that determine quintile 1 and quintile 5. Replacing
  a real crash or repricing with a percentile would suppress the signal the task
  is about. Concretely, in the constructed dataset the largest four-week
  predictor values are genuine market events — CZR at -1.198 log (-70%) at the
  2020-04-03 origin, VXX at +0.729 log (+107%) at the 2020-03-06 origin, DXC at
  -0.541 at 2020-03-06 — all COVID-crash moves that Samartzis's |r| > 0.5 rule
  would have flattened.

  The KR provider defect is a different kind of object (a confirmed data error,
  not a market move), but as recorded in section Z it is also left unchanged in
  this implementation, so no observation of any kind is altered.

This is a meaningful deviation from the source methodology and is listed again
in section AP.

--------------------------------------------------------------------------------
AC. RETURN DEFINITION AND PRICE BASIS
--------------------------------------------------------------------------------

Price basis for returns: ADJUSTED CLOSE
  Samartzis's own features use raw close (his data template has no
  adjusted-close sheet). This project uses adjusted close, for two reasons:
    1. Consistency. Dataset A, the Stage 2 return panel, the 12 rolling-origin
       contexts and every TSFM result in this project are built on adjusted
       close. A baseline built on a different price basis would not be
       comparable.
    2. Correctness. Inspection of the EODHD raw close series shows mechanical
       price jumps at stock splits. Those are not investment returns; treating
       them as returns would inject artificial extreme observations into exactly
       the features and targets that this task ranks on.

Return formula: LOG returns
    r_t = log(P_t / P_{t-1})            P = adjusted close
  Missing wherever either price is missing (pre-inception, and each asset's
  first calendar row). Never replaced with zero.

Cumulative multi-day returns exploit the additive identity
    R_(a,b] = sum_{j=a+1..b} r_j = log(P_b / P_a)
  so every four-week quantity in this stage — the recent four-week predictor,
  the seasonality predictor and the four-week TARGET — is a simple sum of daily
  log returns over an explicit weekday window. Samartzis uses simple returns and
  a compounding product `(1+r).prod()-1`; the log form is the mathematically
  equivalent adaptation for this project's convention. Because the quintile
  target is a cross-sectional RANK, and log is strictly monotone in the simple
  return, the log/simple choice cannot change a single target label; it changes
  only the numerical scale of the return-valued predictors.

  For interpretability the realised target is stored twice:
  `hist_target_log_return` (the sum of daily log returns) and
  `hist_target_simple_return = expm1(log return)`.

Quantities deliberately NOT converted to returns
  Not every OHLCV quantity was turned into a return simply because log returns
  are used elsewhere. The dollar-volume feature (`feat_dollar_volume_2m`) keeps
  its source construction: `log(volume * close / 1000)` with RAW close and RAW
  volume. Raw close x raw volume is the actual currency value traded that day.
  Substituting adjusted close there would multiply a split-adjusted price by an
  unadjusted share count, which is economically meaningless. The absolute-return
  numerator inside `feat_abs_ret_to_volume_3m` DOES use the adjusted-close log
  return, because that component genuinely is a return.

--------------------------------------------------------------------------------
AD. FOUR-WEEK CLASSIFIER ORIGIN FREQUENCY AND THE ORIGIN GRID
--------------------------------------------------------------------------------

The distinction that matters
  DAILY data are required INSIDE features (daily returns, 60-day volatility,
  60-day maximum, daily cross-sectional ranks, rolling volume aggregates) and
  inside the four-week target window. That is completely separate from the
  FREQUENCY at which supervised classifier rows are emitted.

  The released implementation makes this explicit: both `rforest_model.fit` and
  `lgbm_model.fit` in all_models.py downsample their training frame to
  approximately four-week frequency before fitting —
      train_df[train_df['Date'].isin(pd.date_range(end=..., freq='4W-FRI', ...))]
  with the comment "For speed we use monthly frequency (using daily frequency
  slows things down without any increase in performance)". The paper likewise
  defines its time index in four-week periods that it calls "monthly" for
  convenience.

  A prior experimental implementation in this project confirmed why this
  matters: emitting a new 20-weekday target at EVERY weekday produces ~20x more
  rows, each of whose target windows overlaps its 19 neighbours by 19/20, which
  massively inflates effective sample size while adding almost no independent
  information and materially changes the learning problem.

Decision
  Final supervised RF/LGBM observations are emitted ONLY on a four-week-spaced
  grid of Friday forecast origins. Daily intermediate series are computed freely
  inside windows.

The grid
  Anchored on this project's established M6 convention: the grid is the set of
  dates `2022-03-04 + 28k` (k any integer) that lie on the shared weekday
  calendar. Every such date is a Friday, and — verified numerically — every
  consecutive pair is exactly 20 shared weekdays apart, so
      target_end(origin_k) == origin_{k+1}
  holds exactly. This single identity is what makes the causal KNN scheme in
  section AK cheap (one imputation fit per grid date serves both the predictors
  at that date and the target of the preceding origin).

  Eligibility filters applied to the grid:
    - the deepest predictor window must be defined: origin index >= 220 weekdays
      from the start of the calendar;
    - the complete four-week target window must exist within the data;
    - the source methodology's model-history floor: origin >= 2010-01-01.
  The 2010 floor binds (index 220 corresponds to 2009-11-06), so the first
  classifier origin is 2010-01-22.

  Result: 170 origins, 2010-01-22 .. 2023-01-06.
      146 historical
       12 tuning     (section AE below)
       12 M6         (section AM below)
  Stored in `Data/metadata/feature_baseline_origin_schedule.csv` with columns
  origin_index, origin_date, target_start_date, target_end_date, m6_round,
  origin_role, eligible_for_training_from.

  2009 remains pure feature warm-up history: no classifier origin lies in 2009,
  and 2009 observations enter only as the deep end of trailing windows.

  There are no random splits anywhere. All separation is temporal.

The 12 pre-M6 tuning origins — verified, not assumed
  The paper describes tuning over roughly 7 March 2021 to 6 February 2022. The
  released code sets `start_tuning_date = '2021-03-05'`, `end_tuning_date =
  '2022-02-04'` and builds `dates_tuning = pd.date_range(start, end,
  freq='4W-MON')`, then inside the tuning loop takes the FEATURE row from
  `d - BusinessDay(1)` — the preceding Friday.

  Evaluating that expression gives the 12 Mondays
      2021-03-08, 2021-04-05, 2021-05-03, 2021-05-31, 2021-06-28, 2021-07-26,
      2021-08-23, 2021-09-20, 2021-10-18, 2021-11-15, 2021-12-13, 2022-01-10
  whose preceding Fridays are
      2021-03-05, 2021-04-02, 2021-04-30, 2021-05-28, 2021-06-25, 2021-07-23,
      2021-08-20, 2021-09-17, 2021-10-15, 2021-11-12, 2021-12-10, 2022-01-07.

  The same cross-check was run for the released backtest dates
  (`pd.date_range('2022-03-04','2023-02-03',freq='4W-MON')`), which gives the 12
  Mondays 2022-03-07 .. 2023-01-09 whose preceding Fridays are exactly this
  project's 12 M6 origins 2022-03-04 .. 2023-01-06. That is a complete
  confirmation that Samartzis's Monday convention and this project's Friday
  forecast-origin convention describe the SAME forecast points, and it validates
  the tuning translation above.

  Independently, all 12 tuning Fridays sit on this project's own backward grid:
  2022-03-04 - 28k for k = 2..13. Note k = 1 (2022-02-04) is deliberately NOT a
  tuning origin — Samartzis's date_range stops before it — so there is exactly a
  one-period gap between the tuning sample and the M6 sample. That gap is
  preserved.

  The implementation therefore selects the tuning origins as "the last 12 grid
  origins strictly before the first M6 origin, excluding the single grid origin
  immediately preceding it", and asserts that the result begins 2021-03-05 and
  ends 2022-01-07.

  No hyperparameter tuning was performed in this stage. The origins are prepared
  and labelled for the next one.

Training eligibility
  [SUPERSEDED by section AR - the zero-volume rule was later replaced by the
   released Samartzis behaviour; the counts below are pre-correction.]
  Every row carries `eligible_for_training_from = target_end_date`. At any later
  model cutoff T, a historical row t may enter training only if
  `target_end(t) <= T`, so a model never learns from a four-week outcome that
  had not yet occurred. Concretely, using rows with complete features and an
  available target:
      at the first tuning origin (2021-03-05): 12,523 rows over 145 origins
        (no_knn) / 12,714 rows over 145 origins (knn)
      at the first M6 origin (2022-03-04):     13,810 rows over 158 origins
        (no_knn) / 14,008 rows over 158 origins (knn)

--------------------------------------------------------------------------------
AE. THE CLASSIFICATION TARGET — AND THE PAPER/CODE DISCREPANCY
--------------------------------------------------------------------------------

The discrepancy
  The paper describes the feature-based classifiers as using information through
  time t to predict which quintile the asset's return over the NEXT period
  belongs to, and the M6 period is four weeks.

  The released code does something different. In `prepare_data` it computes
  `monthly_returns` (a four-week return) and stores it as
  `train_df['target_return']` — but the label the models actually fit is
      roll_ranks = scores_to_quintiles(returns_df.fillna(0))
      train_df['target'] = roll_ranks
  i.e. the cross-sectional quintile of a SINGLE DAY'S return, and both
  `rforest_model` and `lgbm_model` fit against `train_df['target']`. The stored
  four-week return is never used as the fitted label.

  This project does NOT reproduce that. It implements the target the paper
  describes and the M6 competition requires.

The target implemented
  For each forecast origin t and asset a:
    1. predictors use information available on or before t (section AF);
    2. the realised cumulative return over the NEXT 20 shared weekdays is
           hist_target_log_return(a, t) = sum of r_a,j for j in (t, t+20]
                                        = log(P_a,t+20 / P_a,t)
       with target_start = t+1 weekday and target_end = t+20 weekdays
       (= t + 28 calendar days = the next grid origin);
    3. the cross-section of those realised four-week returns is ranked;
    4. ranks are mapped to the five M6 quintiles with the project's existing
       tie-aware quintile function `rank_to_quintiles`, IMPORTED DIRECTLY from
       `scripts/evaluate_m6_rps.py` so the historical labels use bit-identical
       logic to the official evaluator (rank ascending, quintile index 0 =
       lowest return = Rank1, quintile index 4 = highest = Rank5; a tied block
       receives the average membership of the rank slots it occupies);
    5. `hist_target_quintile` is the argmax of that membership vector, which is
       the ordinary quintile index for any untied asset. The full fractional
       membership is stored alongside it as `hist_target_Rank1..Rank5` so the
       model stage can use either.

  Explicitly: this is a 20-day CUMULATIVE return, not a one-day return shifted
  by 20 days. A unit test asserts that the produced label differs from
  `returns.iloc[t+20]`.

Cross-section membership for the target
  The ranking at origin t covers every asset for which a cumulative four-week
  return can be formed with that branch's data. Cross-section sizes range from
  77 assets (2010-01-22) to 100 (from mid-2021 onwards); the median origin has
  91 rows. Boundaries are computed from the number of assets actually ranked,
  which is how `rank_to_quintiles` already behaves.

  In the KNN branch this cross-section can be 1-2 assets larger than in the
  no-KNN branch, because an asset that listed strictly inside the target window
  has an imputable (hence rankable) four-week return there. This is legitimate
  under the target's information cutoff (section AK) and is one of the two
  mechanisms by which the branches' historical labels differ. It affects 20 of
  170 origins. An alternative convention — restricting the target cross-section
  to assets that already existed at the origin — would make the two branches'
  labels identical; it was NOT adopted because the released implementation ranks
  the full imputed matrix, and because the whole point of the two-pipeline design
  is to let KNN reach the labels wherever it legitimately can. This is flagged
  as a reversible convention in section AP.

Target metadata stored per row
  origin_date, target_start_date, target_end_date, eligible_for_training_from,
  hist_target_log_return, hist_target_simple_return, hist_target_quintile,
  hist_target_Rank1..Rank5, hist_target_cross_section_size,
  hist_target_available.

Observed label distribution (no_knn, all 15,363 rows):
  quintile 0: 3,003   1: 3,081   2: 3,069   3: 3,081   4: 3,129
which is the expected near-uniform result of a per-origin cross-sectional
quintile split with varying cross-section sizes.

--------------------------------------------------------------------------------
AF. FEATURE ALIGNMENT — TRANSLATING THE RELEASED shift(20) INDEXING
--------------------------------------------------------------------------------

Why the released `.shift(20)` calls must NOT be copied
  The released implementation indexes rows by the END of the target period, not
  by the forecast origin. Reading `prepare_data` closely:

    monthly_returns[m] = (1 + returns).prod over rows [m-20, m-1] - 1
                       = P_{m-1} / P_{m-21} - 1
    target             = monthly_returns                    (row m)
    feat_0             = monthly_returns.shift(20)          (row m-20)

  Setting the released row index to `m = t + 21` where t is OUR forecast origin
  makes everything line up:
    target at row m       -> P_{t+20} / P_t - 1   = exactly our four-week target
    feat_0 at row m       -> P_t / P_{t-20} - 1   = the four weeks ending at t
  So the released `.shift(20)` exists purely to convert a target-aligned index
  into origin-aligned information. Copying it into our already origin-aligned
  formulation would apply the lag a SECOND time and push every predictor a month
  further into the past.

  The same translation exposes a one-day inconsistency in the released code. For
  the rolling predictors, `X.rolling(w).agg().shift(20)` evaluated at row
  m = t+21 covers rows [t-w+2, t+1] — one day PAST the forecast origin. feat_0
  and the target are exactly aligned; the rolling features are not. Our
  implementation resolves this in favour of causality: every rolling window ends
  at t inclusive, i.e. [t-w+1, t].

Procedure applied to every feature
  For each of the ten predictors: (1) read the paper's economic/time-window
  description; (2) read the released formula; (3) work out which historical dates
  that formula actually references once the target-aligned index is unwound;
  (4) restate the window explicitly relative to origin t; (5) implement the
  explicit form directly (no `.shift` anywhere in this project's feature code);
  (6) verify numerically.

  Implementation consequence: `features_at_origin()` receives the return matrix
  and an integer origin position and slices closed-form windows such as
  `returns.iloc[i-19 : i+1]`. It cannot in principle reach past the origin. The
  caller additionally passes a return matrix already truncated at the origin, so
  the guarantee is enforced twice.

Numerical verification performed
  - Unit tests recompute the recent four-week return and the seasonality feature
    from synthetic data and compare against explicitly written windows.
  - A "poisoning" unit test overwrites every observation after the origin with a
    large constant and asserts the entire feature block is unchanged.
  - `spot_check_feature_windows()` (run as part of the build) samples 60 random
    complete rows from the real no-KNN dataset and recomputes ALL TEN features
    from first principles in explicit origin coordinates, requiring agreement to
    rtol 1e-9. 600 independent recomputations passed.

--------------------------------------------------------------------------------
AG. THE TEN PAPER-SELECTED PREDICTORS
--------------------------------------------------------------------------------

All windows below are in shared weekdays and are stated relative to forecast
origin t, with t itself INCLUDED (information available at t). r_j denotes the
adjusted-close daily log return on weekday j; P denotes adjusted close; C
denotes RAW close; V denotes raw volume.

Shared intermediate quantity used by features 5 and 6:
    LDV_j   = log(V_j * C_j / 1000)          (undefined, i.e. missing, when
                                              V_j * C_j <= 0)
    D40_j   = 40 * mean(LDV over the available days in [j-39, j])
              defined only once 40 weekdays have elapsed since the asset's
              inception and at least 20 of the 40 days are available.
    When nothing is missing D40 is identical to the released
    `LDV.rolling(40).sum()`; see section AI for the rule and its scope.

1. feat_ret_4w_recent            (released `feat_0`)
   Inputs   adjusted close.
   Formula  sum of r_j for j in [t-19, t]  ==  log(P_t / P_{t-20}).
   Window   the 20 weekdays ending at and including the origin.
   Meaning  the asset's most recent four-week price momentum — the four-week
            period immediately preceding the one being forecast.
   Why it might inform ranking  short-horizon cross-sectional momentum /
            reversal is one of the most studied return predictors.
   Source mapping  `monthly_returns.shift(20)`; translates exactly to [t-19, t]
            with no residual lag.
   Log adaptation  sum of log returns instead of `(1+r).prod()-1`.
   Missing behaviour  requires all 20 daily returns; otherwise missing.
                      Missing in 24 of 15,363 no-KNN rows; 0 in the KNN branch.

2. feat_ret_4w_seasonal_11m      (released `feat_6`)
   Inputs   adjusted close.
   Formula  sum of r_j for j in [t-219, t-200]  ==  log(P_{t-200} / P_{t-220}).
   Window   the ELEVENTH four-week block preceding the origin.
   Derivation  the released `monthly_returns.shift(20*11)` is `feat_0` lagged by
            a further 200 weekdays. Unwinding the target-aligned index
            (m = t+21) puts its price window at P_{t-220} -> P_{t-200}. In the
            paper's units of four-week "months" that is the month-11 block,
            hence "the four-week return approximately 11 months prior". In
            calendar terms the window sits about 9.5-10.5 months before the
            origin, and about 10.6-11.6 months before the target period — the
            comparable point roughly one year earlier.
   Meaning  return seasonality / annual-cycle effects.
   Missing behaviour  requires all 20 daily returns of that block, hence about
            11 months of history. Missing in 284 of 15,363 no-KNN rows (the
            binding constraint for recently listed assets); 0 in the KNN branch.
   This is also the feature that dictates the 2009 warm-up window (section R):
   220 weekdays of history before the earliest 2010 origin.

3. feat_vol_3m                   (released `feat_1`)
   Inputs   adjusted close.
   Formula  sample standard deviation (ddof = 1) of r_j over [t-59, t].
   Window   60 weekdays ending at the origin (~3 months).
   Meaning  recent total return volatility.
   Source mapping  `returns.rolling(60).std().shift(20)`, whose window is
            [t-58, t+1]; shifted back one day here so nothing after t is used.
   Missing behaviour  requires all 60 daily returns. Missing in 73 no-KNN rows.
   Note   DRE's post-acquisition zero-return stretch legitimately produces
          feat_vol_3m = 0 at the last origins.

4. feat_max_ret_3m               (released `feat_2`)
   Inputs   adjusted close.
   Formula  max of r_j over [t-59, t].
   Window   60 weekdays ending at the origin.
   Meaning  the "MAX effect" — the largest single-day gain in the recent past,
            a well-documented lottery-demand proxy that predicts LOW subsequent
            returns.
   Source mapping / missing behaviour  as feature 3 (73 missing, no-KNN).

5. feat_dollar_volume_2m         (released `feat_3`)
   Inputs   RAW close, raw volume. NOT a return.
   Formula  D40_t, i.e. the 40-day aggregate of log(V * C / 1000).
   Window   40 weekdays ending at the origin (~2 months).
   Meaning  a liquidity / size / trading-activity proxy. The paper describes the
            natural log of trading volume x price per share; the released code
            computes that log quantity and then aggregates it over ~40 business
            days, so the feature is 40 x the average log dollar volume (in
            thousands of currency units), not the log of the summed dollar
            volume. That construction is preserved.
   Source mapping  `np.log(volume*close/1000).rolling(40).sum().shift(20)`,
            window [t-38, t+1]; shifted back one day here.
   Price basis  RAW close deliberately — see section AC.
   Missing behaviour  see section AI. Missing in 113 rows in BOTH branches (KNN
            does not touch volume).

6. feat_abs_ret_to_volume_3m     (released `feat_4`)
   Inputs   adjusted close (numerator), RAW close and raw volume (denominator).
   Formula  60 * mean over j in [t-59, t] of ( |r_j| / D40_j ),
            requiring at least 30 available terms.
   Window   60 weekdays ending at the origin, with each term's denominator being
            the 40-day dollar-volume aggregate ending at that SAME day j.
   Source mapping  `(returns.abs() / feat_3).rolling(60).sum().shift(20)` where
            `feat_3` at that point in the released script is the rolling-40 sum
            BEFORE its own `.shift(20)`. That ordering is deliberate in the
            source and is preserved: numerator and denominator are
            contemporaneous. The outer 60-day window is shifted back one day
            here, as for features 3-5.
   Meaning  an Amihud-style illiquidity ratio: how much absolute price movement
            each unit of trading activity is associated with.
   Log adaptation  |r| uses the adjusted-close LOG return.
   Caveat   the denominator is a log-scale aggregate and can approach or cross
            zero for extremely thinly traded assets, which makes the ratio
            unstable there. Measured on the real data: 11 of 15,363 rows have
            D40_t < 40 (an average log dollar volume below 1) and exactly 1 row
            has D40_t <= 0 (VXX at the 2018-06-01 origin). These are the
            provider's genuinely tiny reported share counts for VXX in 2018 and
            SEGA.L in 2011-2012, not a computation error. This is a property of
            the source formula, not something this stage invented, and it was
            not "fixed"; it is recorded here and in section AP.
   Missing behaviour  147 missing rows in both branches.

7-10. feat_rank1_freq_4w, feat_rank2_freq_4w, feat_rank4_freq_4w,
      feat_rank5_freq_4w             (released `feat_Rank1/2/4/5`)
   Inputs   adjusted close (daily returns), all assets.
   Construction
     For each weekday j in [t-19, t]:
       take the cross-section of that day's daily log returns across all assets
       that have a return on day j in this branch's return matrix, and compute
       each asset's tie-aware M6 quintile membership with the SAME
       `rank_to_quintiles` used for the target and for the official evaluator.
     Average those membership vectors over the 20 days.
     Report components 1, 2, 4 and 5.
   Window   the 20 weekdays ending at the origin.
   Why rank 3 is omitted  the five frequencies sum to 1, so the middle
            component is redundant; this follows the source.
   Meaning  how persistently the asset has occupied the extremes of the daily
            cross-sectional return distribution over the past four weeks — a
            direct, model-free description of recent relative behaviour.
   Source mapping  `scores_to_quintiles(returns_df.shift(20))` then
            `.rolling(20).agg(count == q)/20`, whose effective daily-return
            window is [t-18, t+1]; shifted back one day here to [t-19, t].
            The released code uses `pd.qcut(..., labels=False)` per day; this
            project uses its own tie-aware quintile function instead, so that
            one single quintile implementation is used everywhere in the
            project. The two agree whenever there are no ties, and the tie-aware
            version additionally handles a cross-section of fewer than 100
            assets correctly, which matters for early origins.
   CRITICAL distinction  these are DAILY-rank PREDICTORS. They are not the
            target. The target remains the quintile of the FUTURE cumulative
            four-week return (section AE). The released code's conflation of a
            daily-rank quantity with the fitted label is exactly the defect this
            project does not reproduce.
   Missing behaviour  requires the asset to have a return on all 20 days.
            Missing in 24 no-KNN rows; 0 in the KNN branch.

Naming
  Project-native names are used throughout. The mapping to the released
  `feat_*` names is given above and is also embedded in the source code as the
  `FEATURE_NOTES` dictionary in `scripts/build_feature_baseline_dataset.py`.

AI. ZERO / MISSING / NONPOSITIVE VOLUME IN THE VOLUME FEATURES
--------------------------------------------------------------------------------
[SUPERSEDED IN PART by section AR. The FINDINGS below still stand; the "local
rule adopted" and its scope figures were replaced on 2026-08-21 by the released

What was found
  - Raw Dataset D contains 1,946 asset-days with volume exactly 0 (0.62% of
    315,042 rows). No negative and no missing volumes.
  - After calendar alignment and forward filling, zero-volume asset-days rise to
    2,122 out of 328,020 post-inception asset-days (0.647%), affecting 13
    assets.
  - The distribution is overwhelmingly the thinly traded London-listed ETFs:
        SEGA.L 814, IEFM.L 566, IEVL.L 280, HIGH.L 113, DRE 90, SPMV.L 84,
        IEAA.L 70, JPEA.L 53, IUVL.L 28, CHTR 18, VXX 3, MCHI 2, CNC 1
        (post-fill counts; raw counts are alongside them in
        `Data/metadata/dataset_d_preprocessing_summary.csv`).
  - DRE's rise from 1 raw zero-volume day to 90 is entirely mechanical: its
    final genuine observation (2022-10-03) itself reported volume 0, and the
    established forward-fill policy carries that value across the remaining 90
    weekdays.
  - Most of these are not calendar-alignment artefacts but genuine
    non-trading/zero-reported-volume days for illiquid instruments.
  - Separately, eight assets have a MEDIAN reported daily dollar volume below
    $1M, led by SEGA.L at about $5,900. Sampling the raw rows confirms the
    provider genuinely reports single- and double-digit share counts for
    SEGA.LSE and, in 2018, for VXX.US. Those values are preserved.

Why it needs handling at all
  `log(V * C / 1000)` is undefined for nonpositive dollar volume. The released
  code handles this by letting the value become -inf inside a rolling SUM and
  then calling `.replace([inf, -inf], nan)` afterwards, which means a single
  zero-volume day destroys the entire 40-day aggregate. On this dataset that
  rule would have wiped out most of SEGA.L's and IEFM.L's volume features and
  cascaded into `feat_abs_ret_to_volume_3m`.

The local rule adopted (feature construction only)
  1. An asset-day with V * C <= 0 is treated as MISSING in the daily
     log-dollar-volume series. It is not floored, clipped, zero-substituted or
     imputed.
  2. The 40-day aggregate is the MEAN of the available days in the window
     rescaled by 40. When no day is missing this is arithmetically identical to
     the released rolling sum (asserted by a unit test). At least 20 of the 40
     days must be available.
  3. The aggregate additionally stays undefined until a full 40-weekday window
     has elapsed since the asset's inception, so rule 2 relaxes the requirement
     ONLY for genuine zero-volume days and never for a short trading history.
  4. `feat_abs_ret_to_volume_3m` requires at least 30 of its 60 daily terms.

Scope of the effect
  With this rule, `feat_dollar_volume_2m` is missing in 113 of 15,363 rows
  (0.74%) and `feat_abs_ret_to_volume_3m` in 147 (0.96%), identically in both
  branches (the KNN imputation touches only the return matrix, never volume).
  The rule is the sole reason that these two features remain missing in the KNN
  branch, which is why that branch's completeness ceiling is 15,205 rather than
  15,363 rows.

  RAW DATASET D WAS NOT MODIFIED. This is entirely a processed-feature rule.

AJ. TWO COMPLETE PREPROCESSING PIPELINES
--------------------------------------------------------------------------------

Design
  The two variants are NOT "one target dataset with two versions of the
  predictors". Each is a complete pipeline:

    common raw + calendar preparation (Stage 6A)
        |
        +-- variant "knn"     : KNN-process the daily log-return matrix
        |                       -> KNN-branch features
        |                       -> KNN-branch four-week realised returns
        |                       -> KNN-branch historical quintile labels
        |
        +-- variant "no_knn"  : retain genuine missing returns
                                -> no-KNN features
                                -> no-KNN four-week realised returns
                                -> no-KNN historical quintile labels

  One implementation with a `variant` switch — `build_variant(variant, ...)` in
  `scripts/build_feature_baseline_dataset.py`, exposed as
  `--variant {no_knn,knn}` on the CLI. The feature and target mathematics is a
  single shared code path (`features_at_origin`, `target_at_origin`); the only
  thing that differs is which return matrix is handed to it. The pipeline is not
  duplicated.

KNN configuration (variant "knn")
  `sklearn.impute.KNNImputer(n_neighbors=10, weights="distance")`, the released
  configuration, applied to the daily LOG-return matrix (dates x assets, so the
  imputer's "samples" are dates and its "features" are assets, exactly as in the
  released code). The source presents this generically as missing-value
  imputation and gives no further motivation; no additional motivation is
  invented here.

  Two necessary local rules:
    - an asset with NO observation at all by the imputation cutoff has an
      entirely empty column and cannot be imputed; it is left missing. This has
      the useful consequence that the causal scheme never fabricates an asset's
      existence at its own forecast origin;
    - calendar rows that are entirely missing contribute nothing to the fit and
      are excluded from it, then restored as missing.

  What KNN actually reaches on this data: after forward filling, a return is
  missing only in an asset's PRE-INCEPTION period (plus the first calendar row).
  So KNN's practical effect is to give recently listed assets a synthetic
  pre-inception return history, which lets their trailing feature windows fill.

Variant "no_knn"
  No imputation of any kind. Genuine missing returns are preserved. Where a
  feature or a target cannot be formed from available observations, it is left
  unavailable rather than manufactured. No substitute imputation method was
  introduced to remove NaNs.

Row-existence rule (identical in both branches)
  A supervised row (t, a) exists only if asset a has a genuine adjusted-close
  observation on or before t. Both branches therefore emit 15,363 rows over 170
  origins (77 to 100 assets per origin). The branches differ in the CONTENT of
  those rows, not in which (origin, asset) pairs are attempted.

--------------------------------------------------------------------------------
AK. KNN CAUSALITY
--------------------------------------------------------------------------------

The problem
  Fitting one KNN imputer to the whole 2009-2023 matrix — as the released code
  does, before any backtest date exists — lets 2023 observations influence how a
  2011 return is imputed, and therefore contaminates every historical forecast
  the backtest recreates. That is unacceptable in a rolling-origin backtest.

Two different, deliberately different, information cutoffs
  PREDICTORS at forecast origin t
      may use information dated <= t only. Any KNN-imputed return that enters a
      predictor at t must come from a fit containing no observation later than
      t. Nothing after t may influence predictors at t.

  HISTORICAL TARGET for origin t
      deliberately describes what happened AFTER t. Its four-week window ends at
      target_end(t). If missing returns inside that window need KNN processing,
      that processing may use information through target_end(t) — by the time
      the label is knowable, those observations have occurred. It must not use
      anything later than target_end(t).

  Formally:
      predictor construction for t        : information <= t
      KNN target construction for t       : information <= target_end(t)

Training eligibility
  At a later model cutoff T, historical row t may enter training only if
  target_end(t) <= T. Stored on every row as `eligible_for_training_from`.
  A model therefore never learns from a four-week outcome that had not yet
  happened at that point in history.

Implementation, and why it is cheap
  Because consecutive grid origins are exactly HORIZON = 20 shared weekdays
  apart, target_end(origin_k) == origin_{k+1} exactly. So ONE causal KNN fit per
  grid date serves two purposes at once:
      the fit at cutoff g -> predictors at origin g
                          -> historical target of origin g - 20 weekdays
  The build therefore performs 171 KNN fits (170 origins + one final fit at the
  last target_end, 2023-02-03), not one per weekday, and never holds more than
  one imputed matrix in memory. Wall time for the KNN branch: about 6 minutes.
  A daily-frequency causal KNN backtest framework was explicitly not built,
  because the classifier origins are four-week spaced and would not use it.

  Note that the no-KNN branch needs no cutoff logic at all: its features are
  causal by construction, so it is computed directly from the single processed
  return panel.

How leakage was tested (positive and negative controls)
  In `verify_knn_causality()`, run as part of every full build, at the first
  tuning origin (2021-03-05):
    - PREDICTORS: every return after the origin is overwritten with a large
      constant (9.0), the causal imputation and feature block are rebuilt, and
      the result is required to be exactly equal to the uncorrupted block.
      PASSED.
    - Negative control: corrupting returns INSIDE the predictor windows must
      change the features, otherwise the test above would be vacuous. PASSED
      (the features do change).
    - TARGET: corrupting every return after target_end must leave the historical
      label unchanged. PASSED.
    - Negative control: corrupting returns INSIDE the target window must change
      the label. PASSED.
  Unit tests add: KNN imputation is unchanged by post-cutoff corruption; the
  imputed frame has exactly cutoff+1 rows; an asset with no history at the
  cutoff stays entirely missing (it cannot be fabricated before it exists).
  A further unit test poisons all post-origin data and asserts the whole
  feature block is unchanged, which covers the no-KNN branch as well.

--------------------------------------------------------------------------------
AL. NO FEATURE NORMALIZATION AT THIS STAGE
--------------------------------------------------------------------------------

The paper contains a general statement that scale-sensitive models are
normalized. Inspection of the released implementations shows this is NOT applied
uniformly: `rforest_model` and `lgbm_model` consume their feature inputs
directly with no StandardScaler-style step, while models that actually need it
(e.g. `mlp_model`) do their own scaling internally.

RF and LightGBM are tree ensembles and are invariant to monotone rescaling of
individual features, so a global standardisation would add nothing but would
make the stored features less interpretable and would introduce a fitted
statistic that itself needs a causal cutoff.

Decision: the ten predictors are stored exactly as engineered. No
standardisation, normalisation, scaling or centring is applied in this stage.
If any later model requires scaling, that becomes an explicit, documented
model-stage decision with its own causality treatment.

Design choice
  Everything is materialised; nothing is generated on demand. The concern that
  motivated a dynamic design — that causal KNN is cutoff-specific and would
  require dozens of near-duplicate large files — dissolves once the grid

--------------------------------------------------------------------------------
AP. LIMITATIONS AND DEVIATIONS FROM SAMARTZIS
--------------------------------------------------------------------------------

Deliberate methodological deviations
  1. NO ECOD, NO WINSORISATION. Genuine extreme returns are retained
     (section AB).
  2. ADJUSTED CLOSE, not raw close, for all return quantities; LOG returns, not
     simple returns (section AC). Raw close is retained only where it is
     economically correct, inside the dollar-volume product.
  3. THE PAPER'S TARGET, not the released code's. The label is the
     cross-sectional quintile of the realised cumulative FOUR-WEEK return, not
     the quintile of a single daily return (section AE).
  4. CAUSAL KNN. The released code fits one imputer to the entire sample before
     backtesting; here the KNN fit is re-done per origin with an explicit
     information cutoff (section AK).
  5. SOURCE INDEXING TRANSLATED, NOT COPIED. `.shift(20)` / `.shift(220)` are
     not reproduced; every window is restated in forecast-origin coordinates,
     which also removes the released code's one-day look-ahead in its rolling
     features (section AF).
  6. THE PAPER'S FINAL FEATURE SET ONLY. The code-only quarterly-return `feat_5`
     and the four intraday/volume-change candidates are excluded (section AH).
  7. TIE-AWARE QUINTILES from this project's official evaluator instead of
     `pd.qcut`, everywhere a cross-sectional quintile is formed.
  8. [WITHDRAWN - see section AR] A local zero-volume rule was originally used
     in place of the released behaviour. It was reconsidered and removed, so
     the zero-volume handling is now the released Samartzis behaviour exactly
     and is NOT a deviation.
  9. NO GLOBAL NORMALISATION for RF/LGBM inputs (section AL).

Known limitations
  a. THE KR ADJUSTED-CLOSE PROVIDER DEFECT IS PRESENT, by decision. It
     contaminates a handful of KR's own features and its Dataset-D historical
     label for the origin 2022-10-14. It does not touch the official evaluation
     (section Z).
  b. DATASET D IS SINGLE-PROVIDER, and adjusted closes are recomputed
     retrospectively by providers, so a future re-download may not reproduce
     these numbers exactly. The KR break is a concrete illustration of that
     fragility.
  c. THE ILLIQUIDITY FEATURE IS UNSTABLE FOR VERY THIN ASSETS. Because the
     released formula divides by a LOG-scale aggregate, the denominator can
     approach zero: 11 of 15,363 rows have D40 < 40 and one has D40 <= 0
     (VXX, 2018-06-01 origin), producing values two orders of magnitude larger
     than typical and, in that one row, of the wrong sign. This is inherited
     from the source construction and was preserved rather than redesigned. The
     model stage may wish to consider it.
  d. SOME REPORTED VOLUMES ARE IMPLAUSIBLY SMALL. EODHD reports single- and
     double-digit daily share counts for SEGA.LSE throughout, and for VXX.US in
     2018. These are likely single-venue prints rather than consolidated tape.
     The values were retained (Dataset D is used as acquired), but any
     conclusion that leans on the two volume features for those assets should be
     treated cautiously.
  e. KNN FABRICATES PRE-INCEPTION RETURN HISTORY in the "knn" branch. That is
     precisely the thing the no-KNN branch exists to test, and the causal scheme
     confines it (an asset with no history at its own origin gets no row at
     all), but it is a fabrication and should be described as such in the
     report. It is the direct source of the KNN branch's 199 extra usable rows.
  f. THE TARGET CROSS-SECTION CONVENTION IS REVERSIBLE. Including
     imputable-but-not-yet-listed assets in the KNN branch's target ranking
     (section AE) is what produces the 40 differing labels. Restricting the
     ranking to assets that existed at the origin would make the two branches'
     labels identical and is a defensible alternative. Flagged rather than
     silently chosen.
  g. THE 2010 FLOOR plus the 220-weekday lookback means the earliest origin is
     2010-01-22 and early origins rank only 77-84 assets. Quintile boundaries
     are computed from the actual cross-section size, so this is handled
     correctly, but early-period labels are formed over a smaller universe than
     the M6 rounds.
  h. THE UNIVERSE IS THE FIXED M6 LIST, carrying that list's survivorship
     characteristics.
  i. THE PAPER PDF IS NOT IN THIS REPOSITORY. The paper's methodology was taken
     from the project specification and cross-checked against the released code
     and README; the final feature list in section AG is the paper's reported
     set as specified. If the PDF becomes available, section AG's feature list
     and the seasonality window in particular should be re-verified against it.

--------------------------------------------------------------------------------
AR. CORRECTION — THE ZERO-VOLUME RULE WAS REPLACED BY THE RELEASED SAMARTZIS
    BEHAVIOUR (applied 2026-08-21)
--------------------------------------------------------------------------------

Supersedes: the "local rule adopted" paragraph of section AI, deviation 8 of
section AP, and the affected counts in sections AD and AJ. Everything else in
Stage 6 stands unchanged.

What was reconsidered
  Stage 6 originally adopted a custom treatment for zero/nonpositive dollar
  volume: invalid days were dropped from the 40-day aggregate, which was
  computed as the mean of the available days rescaled by 40 (>= 20 of 40
  required), and the 60-day absolute-return-to-volume feature required only
  30 of its 60 terms. That was a deviation from the released implementation,
  which lets log(0) become -inf and destroys any window containing it.

Evidence gathered (read-only check, `check/zero_volume_method_check.txt`,
a temporary artifact not part of the pipeline)
  The two treatments were computed side by side over all 15,363 supervised rows
  with every other methodological decision held fixed:
    - missing feat_dollar_volume_2m      : 113 (0.74%) -> 382 (2.49%)
    - missing feat_abs_ret_to_volume_3m  : 147 (0.96%) -> 521 (3.39%)
    - fully usable rows, no_knn          : 15,006 -> 14,739  (-267, -1.78%)
    - fully usable rows, knn             : 15,205 -> 14,842  (-363, -2.39%)
    - M6 prediction rows with a missing volume feature: 3 -> 28 of 1,200
    - no origin is lost in any scope (170 / 145 / 158 origins unchanged)
  The loss is concentrated, not broad: in the no-KNN branch 11 assets are
  affected and SEGA.L (87), IEFM.L (61) and HIGH.L (29) account for 66% of the
  lost rows; eight of the eleven are the thinly traded London-listed ETFs.
  Mechanism: one invalid day removes up to 40 consecutive 40-day aggregates,
  and each removed aggregate removes up to 60 consecutive ratio terms, so a
  single zero-volume day can suppress the ratio feature for ~99 weekdays.

Decision
  The released Samartzis behaviour is adopted exactly. The custom rule is
  withdrawn. This makes the zero-volume handling faithful to the source rather
  than an adaptation, at the cost of ~1.8% (no_knn) / ~2.4% (knn) of usable
  training rows and 28 of 1,200 M6 prediction rows carrying a missing volume
  feature.

Implementation now in force
      LDV_j = log(V_j * C_j / 1000)          undefined -> missing
      D40_t = STRICT 40-day rolling sum of LDV over [t-39, t]
              (min_periods == window, so any invalid day, or fewer than 40
               weekdays since inception, leaves it undefined)
      feat_abs_ret_to_volume_3m
            = STRICT 60-day sum over j in [t-59, t] of |r_j| / D40_j
  Marking an invalid day as missing and summing strictly is arithmetically
  identical to the released `-inf` propagation followed by
  `.replace([inf, -inf], nan)`; verified over the full panel (identical NaN
  pattern, identical finite values, 50,301 undefined cells either way), and
  asserted by a unit test that compares against the literal source expression.
  The established forecast-origin alignment is unchanged: the windows are still
  [t-39, t] and [t-59, t] with t included, so the released `.shift(20)`
  indexing issue is NOT reintroduced.

Resulting counts (both branches, 15,363 rows over 170 origins)
    missing feat_dollar_volume_2m         382 (2.49%)   identical in both
    missing feat_abs_ret_to_volume_3m     521 (3.39%)   identical in both
    fully usable rows   no_knn 14,739     knn 14,842
    usable at the first tuning origin (2021-03-05): 12,299 / 12,396
    usable at the first M6 origin (2022-03-04):     13,568 / 13,670
    M6 prediction rows with a missing volume feature: 28 of 1,200, in all 12
      rounds, involving only SEGA.L, IEFM.L, HIGH.L and DRE
  The model stage must now decide explicitly how each model treats those rows:
  LightGBM consumes missing values natively; Random Forest cannot.
