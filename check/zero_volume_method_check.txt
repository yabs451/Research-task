SCOPE AND METHOD
----------------
This compares ONLY the zero/nonpositive-volume handling. Everything else is held
fixed: the same processed Dataset D panels, the same shared weekday calendar and
forward-fill policy, the same 170 four-week Friday forecast origins, the same
forecast-origin window alignment (the released .shift(20) indexing issue is NOT
reintroduced), the same log-return conventions, the same other eight features,
the same targets.

  CURRENT behaviour (what is implemented today)
      LDV_j  = log(V_j * C_j / 1000), undefined -> MISSING (not -inf)
      D40_t  = 40 * mean(LDV over available days in [t-39, t]),
               needs >= 20 of 40 available, and >= 40 weekdays since inception
      feat_abs_ret_to_volume_3m
             = 60 * mean over j in [t-59, t] of (|r_j| / D40_j),
               needs >= 30 of 60 terms

  SOURCE-STYLE behaviour (exact Samartzis zero-volume semantics)
      feat_3 = np.log(volume * close / 1000)          -> -inf on zero volume
      feat_3 = feat_3.rolling(40).sum()               -> -inf if ANY day invalid
                     .replace([inf,-inf], np.nan)     -> NaN
      feat_4 = (returns.abs() / feat_3).rolling(60).sum()   -> strict, NaN-prop
      i.e. one invalid day destroys the whole aggregate.

  Implementation note: -inf was modelled exactly but computed safely, as
  "strict rolling(40).sum() over the finite values, set to NaN wherever the
  window contains >= 1 invalid day". This is arithmetically identical to letting
  -inf propagate and then replacing it, without float-inf edge cases in pandas.

  Sanity check performed: the recomputed CURRENT feature values reproduce the
  stored columns in supervised_rows_no_knn.csv exactly (assert passed), so the
  source-style figures below are measured against a verified baseline.

  Row universe: the 15,363 supervised (origin, asset) rows over 170 origins,
  identical in both preprocessing branches. The two volume features are
  branch-independent (KNN never touches volume), so their missing counts are the
  same in both branches; the branches differ only in how many rows the OTHER
  eight features complete, which is why the "rows lost" totals differ.

7. WHY VALUES GO MISSING UNDER SOURCE-STYLE BEHAVIOUR
-----------------------------------------------------

7a. TRACE — SEGA.L at the M6 Round 1 origin, 2022-03-04
    (feat_dollar_volume_2m: defined today, NaN under source-style)

    40-weekday window: 2022-01-10 .. 2022-03-04
    Zero-volume days in that window: 15 of 40
      first three: 2022-01-12, 2022-01-19, 2022-01-20

        date        raw close   volume   volume*close/1000   log(.)
        2022-01-12   108.405      0            0.0           -inf
        2022-01-19   107.690      0            0.0           -inf
        2022-01-20   107.585      0            0.0           -inf

    Step by step:
      zero volume
        -> volume * close / 1000 = 0
        -> log(0) = -inf                                (invalid value)
        -> rolling(40).sum() over the window = -inf     (one term dominates)
        -> .replace([inf,-inf], nan) = NaN              (feature lost)
        -> the row loses 1 of its 10 predictors

    Values:
      feat_dollar_volume_2m  SOURCE-STYLE = NaN
      feat_dollar_volume_2m  CURRENT      = 82.4038
                                          = 40 x mean of the 25 available days
                                          = 40 x 2.0601

    Downstream, same row:
      the 60-day ratio window 2021-12-13 .. 2022-03-04 needs a denominator D40_j
      for each of its 60 days. Under source-style ALL 60 of those denominators
      are NaN (SEGA.L has zero-volume days throughout that stretch), so the
      strict rolling(60).sum() is NaN and feat_abs_ret_to_volume_3m is lost too.

      => row (2022-03-04, SEGA.L) has 2 of 10 features missing under
         source-style, and is fully complete under the current rule.

7b. TRACE — IEFM.L at the M6 Round 7 origin, 2022-08-19
    (dollar-volume feature survives, ratio feature is still lost)

    Its own 40-day window 2022-06-27 .. 2022-08-19 happens to contain no
    zero-volume day, so feat_dollar_volume_2m = 301.7552 under BOTH rules.

    But the ratio feature needs D40_j for every j in 2022-05-30 .. 2022-08-19,
    and 50 of those 60 days have their OWN 40-day window reaching back into the
    earlier zero-volume stretch (first such day: 2022-06-08). Under source-style
    those 50 denominators are NaN, the strict rolling(60).sum() propagates NaN,
    and feat_abs_ret_to_volume_3m is lost while the dollar-volume feature is
    not.

    Contamination radius: ONE invalid day poisons up to 40 consecutive D40
    values, and each poisoned D40 poisons up to 60 consecutive ratio values, so
    a single zero-volume day can remove the ratio feature for up to ~99
    consecutive weekdays — roughly five four-week origins.

    CNC is the cleanest illustration of the mechanism: it has exactly ONE
    zero-volume day in fourteen years. Under the current rule its D40 is
    undefined on 39 days (the inception ramp only). Under source-style it is
    undefined on 79 days — the same 39, plus exactly 40 more, i.e. every window
    that contains that single day. Those extra 40 weekdays span two four-week
    origins, which is where CNC's 5 lost rows come from.

    HIGH.L shows the compounding case: 113 zero-volume days remove 693 D40
    values (about 6 per zero day, because the zero days are scattered rather
    than clustered), versus 45 under the current rule.
